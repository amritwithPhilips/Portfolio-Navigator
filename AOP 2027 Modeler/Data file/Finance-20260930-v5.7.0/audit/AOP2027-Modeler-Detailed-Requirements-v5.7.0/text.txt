 
 
AOP 2027 Modeler Detailed Requirements 
Version 5.7.0  |  30 September 2026  |  Companion to PRD v5.7.0 
 
This document defines detailed requirements for AOP 2027 Modeler v5.7.0. Each requirement 
includes an ID, title, description, acceptance criteria, affected tab(s), and priority. Requirements use 
language: MUST (mandatory), SHOULD (recommended), MAY (optional). Companion document: 
AOP2027-Modeler-PRD-v5.7.0.docx. 
Requirement groups: EXCO (ExCo hierarchy, filter, demand, trade-off, AOP protection); BEN (benefit 
classification, display, data quality); UI (toggles, levers, KPIs, charts, filters, reset); FIN (finance model, 
unchanged from v5.0). 
ExCo Accountability Requirements 
EXCO-01  ExCo Accountability Hierarchy 
Description: The engine MUST maintain a mapping of 16 ExCo members to all 35 organisation values. The 
mapping MUST be implemented as two complementary data structures plus a fuzzy match function.  
Implementation: 
• EXCO_HIERARCHY: dictionary keyed by leader name. Each entry contains role (string), segment 
(string), and orgs (array of organisation values). 
• ORG_TO_EXCO: reverse lookup dictionary mapping each of the 35 organisation values to its ExCo 
leader name. 
• excoOf(orgName): fuzzy match function that handles whitespace differences, encoding variations, 
and case-insensitive matching to return the ExCo leader for any organisation string. 
• enrich() MUST add an exco field to every Programs row using ORG_TO_EXCO/excoOf().

• Tab 2: ExCo filter applies to both the Demand in Scenario table and the Prioritized Programs filters.

EXCO-04  ExCo Trade-off Cockpit 
Description: An interactive trade-off panel MUST be available on Tabs 3 (Functions & Regions) and 4 (BU 
Led) enabling per-ExCo leader budget negotiation. 
Implementation: 
• Position: below the filter bar on Tabs 3 and 4. 
• Default state: collapsed/closed. Opens automatically when trade-off budget values are entered. 
• Columns per ExCo leader row: Requested, Funded, Gap, % Funded, Hard Ben, Soft Ben, Trade -off 
Budget (input), Delta, Progs/Benefits impact. 
• Trade-off Budget: user enters a target funding amount. Delta = Trade -off Budget - current Funded. 
• Progs/Benefits impact: shows Programs count + Hard/Soft benefit M€ that would be added or 
removed if Apply is pressed. 
• Apply button: includes/excludes P4 Programs by merit score ranking to match entered trade -off 
budgets. Creates decision log entries. Does NOT modify Total AOP (see EXCO -05). 
• Reset button: clears all entered trade-off budget values in one click. 
• Negative trade-offs: entering a budget below current funded amount models reductions. Lowest -
merit P4 Programs are excluded first. Delta shown in red. 
• Implementation uses batched transact() calls to avoid rendering issues during Apply.  
Acceptance Criteria: 
• AC-1: Trade-off cockpit visible on Tabs 3 and 4 when expanded. 
• AC-2: Entering a budget value opens the cockpit if closed. 
• AC-3: Apply includes/excludes correct Programs by merit ranking. 
• AC-4: Apply creates decision log entries for each Programs change. 
• AC-5: Apply does NOT change the Total AOP value. 
 
 
• AC-6: Reset clears all budget inputs and reverts Programs changes. 
• AC-7: Negative trade-off reduces funding by excluding lowest-merit P4 Programs. 
• AC-8: No blank page or rendering error during Apply (batched transact).  
Tab(s): 3, 4. Priority: P1 (Must Have). 
EXCO-05  Total AOP Protection 
Description: The Total AOP (M€) field MUST change only via manual user edit. No automated process 
(including Trade-off Apply) may modify it. 
Implementation: 
• Trade-off Apply button includes/excludes Programs but does NOT modify the Total AOP budget value.  
• "On top off AOP" KPI displays the delta between actual allocation and user -set budget. 
• Tabs 3 & 4: "On top off AOP" shown as a KPI tile. Red when over-budget, green when under. 
• Tab 2: Allocated AOP shows "On top off: +X M€" (red) or "Under budget: X M€" (green).  
• Total AOP changes ONLY when the user manually edits the budget input field on Tab 2.  
• Presets do not change Total AOP. They only change lever settings. 
Acceptance Criteria: 
• AC-1: After Trade-off Apply, Total AOP value is unchanged. 
• AC-2: "On top off AOP" KPI shows correct delta. 
• AC-3: Red indicator when allocation exceeds budget. 
• AC-4: Green indicator when allocation is within budget. 
• AC-5: Manual edit of Total AOP input field updates the budget and all dependent calculations.  
• AC-6: Preset application does not modify Total AOP. 
Tab(s): 2, 3, 4. Priority: P1 (Must Have).

Finance calculation module — v5.7.0 
The finance module is the calculation authority for Programs allocation and combined Programs 
+ Operations recipient cost. The source-accountability view and the receiving-BU view represent 
the same cost and must never be added together. 
Confirmed default and charging key 
The Optimal default budget is 100 M€. LFR retains the verified share; Carry Over uses approved 
baseline caps without an ROI threshold; Sustain is 60% of its bucket; Value uses the remaining 
available budget; IT Simplification is optional and inactive by default. Manual changes retain any 
overspend visibly. PMI is on top. 
EW charge to recipient b = funded EW Programs × charging fraction b. The BU row 276 
percentage formulas sum to 0.001 because recipient values totaling 40 are divided by 40,000. 
The confirmed correction multiplies each source fraction by 1,000. It preserves the exact 
22.63033175355452% unallocated share. Display rounding does not change the calculation. 
FIN-01 
One exact financial ledger feeds all six tabs, Portfolio Inclusion Table, both ExCo Trade-off 
Cockpits, AOP2027: Programs Demand Overview, Organisation IT Cost Allocation: Programs + 
Operations, and exports. 
FIN-02 
Separate demand selection from allocation. First compute requested, automatic, manual, final 
and unfunded for every active Programs record. Then allocate final funding using the 
appropriate source key. Allocation never changes merit or funding. 
FIN-03 
Single BU: use the row’s exact spend-allocation percentages, including sub-BU recipients. A 
confirmed sole recipient can receive 100% only when the source establishes that recipient; 
never substitute the requesting organisation for a missing charge key. 
FIN-04 
Cross BU: allocate final amount using the record’s exact percentages from SPEND ALLOCATION 
BY BUSINESS UNIT. Validate each recipient and row total. Do not redistribute an incomplete key 
automatically. 
FIN-05 
Indirect Cross BU follows its own source allocation, including Not allocated to BU. The 
requesting Function/Region remains the accountable origin. No fallback to the EW key is 
applied. 
 
 
FIN-06 
Enterprise-wide: isolate the Enterprise-wide charging row and apply its validated percentage 
vector to funded EW amounts. Retain both source Function/Region and recipient BU for drill-
down. 
FIN-07 
PMI remains funded on top of the 100 M€ envelope, separately identified and not charged to 
BUs. Unknown types remain explicitly unmapped until a valid source routing exists. 
FIN-08 
Retain exact source percentage precision. Apply the confirmed 1,000× correction only to an EW 
vector totaling 0.001; accept a fraction vector totaling 1 directly. Other EW totals are 
exceptions. BU row percentages are never silently normalized. Missing balances remain 
Unallocated. 
FIN-09 
Programs total uses investment spend, not operating-expense-only cost. Source capitalization 
and expense splits may be shown separately; spend = capitalization + expense. Do not substitute 
COST ALLOCATION columns for total investment allocation. 
FIN-10 
Operations follows its independent Bill of IT allocation, not the Programs EW key. Each service 
ID has one cost and many traceable allocations. Keep own consumption, Region allocation and 
Function allocation separate before summing recipient cost. 
FIN-11 
Show accountability/consumption and receiving-BU charge as two views of the same cost. 
Never add Functions/Regions sender totals to their already allocated BU recipients. Seven top-
level Operations recipient clusters reconcile to all 182 service costs. 
FIN-12 
Charge[b] = Single BU[b] + Cross BU[b] + Indirect Cross BU[b] + EW[b] + Operations own[b] + 
Operations Region[b] + Operations Function[b]. Group total also includes explicit pending 
allocation and separately retained PMI. 
FIN-13 
Confirmed carry-over baseline cap; no ROI threshold. 
FIN-14 
Benefits accepted for prioritization; no benefit-only hold. 
 
 
FIN-15 
Exclude missing-request records from active Programs overviews, prioritization and exports. 
Nine such records remain in the refreshed source. Preserve original cells and exclusion reasons. 
A completed record can return on refresh. 
FIN-16 
Exclude uninterpretable source decision records such as Excel errors and numeric zero decisions 
from active scope; list IDs, source cells and amounts in the audit. Blank decisions remain
