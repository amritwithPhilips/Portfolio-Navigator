AOP 2027 Modeler Detailed Requirements
Version 5.4  |  28 September 2026  |  Companion to PRD v5.3

This document defines detailed requirements for AOP 2027 Modeler v5.2. Each requirement includes an ID, title, description, acceptance criteria, affected tab(s), and priority. Requirements use language: MUST (mandatory), SHOULD (recommended), MAY (optional). Companion document: AOP2027-Modeler-PRD-v5.2.docx.
Requirement groups: EXCO (ExCo hierarchy, filter, demand, trade-off, AOP protection); BEN (benefit classification, display, data quality); UI (toggles, levers, KPIs, charts, filters, reset); FIN (finance model, unchanged from v5.0).
ExCo Accountability Requirements
EXCO-01  ExCo Accountability Hierarchy
Description: The engine MUST maintain a mapping of 16 ExCo members to all 35 organisation values. The mapping MUST be implemented as two complementary data structures plus a fuzzy match function.
Implementation:
EXCO_HIERARCHY: dictionary keyed by leader name. Each entry contains role (string), segment (string), and orgs (array of organisation values).
ORG_TO_EXCO: reverse lookup dictionary mapping each of the 35 organisation values to its ExCo leader name.
excoOf(orgName): fuzzy match function that handles whitespace differences, encoding variations, and case-insensitive matching to return the ExCo leader for any organisation string.
enrich() MUST add an exco field to every programme row using ORG_TO_EXCO/excoOf().
ExCo Member Mapping:

Acceptance Criteria:
AC-1: EXCO_HIERARCHY contains exactly 16 entries.
AC-2: ORG_TO_EXCO maps all 35 unique organisation values.
AC-3: excoOf() returns a valid leader for every org value in the demand dataset.
AC-4: Every enriched programme row has a non-null exco field.
AC-5: Regional leaders (IR, NAM, GCR) receive both BU and EW demand from their orgs.
Tab(s): All. Priority: P1 (Must Have).
EXCO-02  Global ExCo Filter
Description: ExCo Leader MUST be added as the first filter dropdown on all programme tabs. The filter MUST cascade to downstream filters.
Implementation:
ExCo Leader dropdown is the first filter element on Tabs 2, 3, 4, and Tab 6 overview.
Cascade chain: ExCo -> Organisation -> Platform. Selecting an ExCo leader narrows Organisation options to only that leader's mapped organisations.
Organisation selection further narrows Platform options to platforms present in those organisations' demand.
AND logic with all other filter dimensions (Funding Status, Type, Investment Area, text search).
Tab 2: ExCo filter applies to both the Demand in Scenario table and the Prioritized programme filters.
Acceptance Criteria:
AC-1: ExCo filter dropdown present on Tabs 2, 3, 4, 6.
AC-2: Selecting "Jie Xue" shows only CT, DXR, MR, PDU organisations.
AC-3: Clearing ExCo filter restores all organisations in the Org filter.
AC-4: ExCo + Org + Platform filters combine with AND logic.
AC-5: Filter option counts update dynamically reflecting other active filters.
Tab(s): 2, 3, 4, 6. Priority: P1 (Must Have).
EXCO-03  Demand Split by ExCo (Tab 1)
Description: The Demand Split table on Tab 1 MUST be reorganised from a flat organisation list to collapsible ExCo groups.
Implementation:
Each ExCo leader appears as a collapsible parent row.
Parent row shows: programme count, requested M€, prioritised M€, gap M€, % funded, hard benefits M€, soft benefits M€, operations cost M€.
Click to expand: constituent organisations shown as child rows with the same columns.
Colour-coded funding percentage: red for low (<50%), amber for medium (50-80%), green for high (>80%).
Replaces the previous "Demand Split by Organisation" flat table.
Acceptance Criteria:
AC-1: 16 ExCo parent rows visible (when all have demand).
AC-2: Expanding any ExCo row shows its constituent organisations.
AC-3: Parent row totals equal sum of child row values.
AC-4: Hard and Soft benefit columns populated for all rows.
AC-5: Percentage-funded values correctly colour-coded.
Tab(s): 1. Priority: P1 (Must Have).
EXCO-04  ExCo Trade-off Cockpit
Description: An interactive trade-off panel MUST be available on Tabs 3 (Functions & Regions) and 4 (BU Led) enabling per-ExCo leader budget negotiation.
Implementation:
Position: below the filter bar on Tabs 3 and 4.
Default state: collapsed/closed. Opens automatically when trade-off budget values are entered.
Columns per ExCo leader row: Requested, Funded, Gap, % Funded, Hard Ben, Soft Ben, Trade-off Budget (input), Delta, Progs/Benefits impact.
Trade-off Budget: user enters a target funding amount. Delta = Trade-off Budget - current Funded.
Progs/Benefits impact: shows programme count + Hard/Soft benefit M€ that would be added or removed if Apply is pressed.
Apply button: includes/excludes P4 programmes by merit score ranking to match entered trade-off budgets. Creates decision log entries. Does NOT modify Total AOP (see EXCO-05).
Reset button: clears all entered trade-off budget values in one click.
Negative trade-offs: entering a budget below current funded amount models reductions. Lowest-merit P4 programmes are excluded first. Delta shown in red.
Implementation uses batched transact() calls to avoid rendering issues during Apply.
Acceptance Criteria:
AC-1: Trade-off cockpit visible on Tabs 3 and 4 when expanded.
AC-2: Entering a budget value opens the cockpit if closed.
AC-3: Apply includes/excludes correct programmes by merit ranking.
AC-4: Apply creates decision log entries for each programme change.
AC-5: Apply does NOT change the Total AOP value.
AC-6: Reset clears all budget inputs and reverts programme changes.
AC-7: Negative trade-off reduces funding by excluding lowest-merit P4 programmes.
AC-8: No blank page or rendering error during Apply (batched transact).
Tab(s): 3, 4. Priority: P1 (Must Have).
EXCO-05  Total AOP Protection
Description: The Total AOP (M€) field MUST change only via manual user edit. No automated process (including Trade-off Apply) may modify it.
Implementation:
Trade-off Apply button includes/excludes programmes but does NOT modify the Total AOP budget value.
"On top off AOP" KPI displays the delta between actual allocation and user-set budget.
Tabs 3 & 4: "On top off AOP" shown as a KPI tile. Red when over-budget, green when under.
Tab 2: Allocated AOP shows "On top off: +X M€" (red) or "Under budget: X M€" (green).
Total AOP changes ONLY when the user manually edits the budget input field on Tab 2.
Presets do not change Total AOP. They only change lever settings.
Acceptance Criteria:
AC-1: After Trade-off Apply, Total AOP value is unchanged.
AC-2: "On top off AOP" KPI shows correct delta.
AC-3: Red indicator when allocation exceeds budget.
AC-4: Green indicator when allocation is within budget.
AC-5: Manual edit of Total AOP input field updates the budget and all dependent calculations.
AC-6: Preset application does not modify Total AOP.
Tab(s): 2, 3, 4. Priority: P1 (Must Have).
Benefit Classification Requirements
BEN-01  Benefit Classification Engine
Description: The engine MUST classify every programme into one of four benefit categories using a deterministic classifyBenefit() function.
Classification Rules:

Enriched fields per programme row:
benefitClass: "hard" | "soft" | "qualitative" | "none"
benefitClassLabel: "Hard Benefit" | "Soft Benefit" | "Qualitative Only" | "No Benefit Data"
benefitFlag: data quality flag string or null
Data Quality Flags:

Acceptance Criteria:
AC-1: Every enriched row has benefitClass, benefitClassLabel, and benefitFlag fields.
AC-2: classifyBenefit() is deterministic — same inputs always produce same classification.
AC-3: Hard areas list is exactly: Revenue Increase, Productivity Savings.
AC-4: Programmes with benefit > 0 in any area not in the Hard list classify as Soft.
AC-5: Programmes with zero/null benefit but non-empty impact/problem text classify as Qualitative.
AC-6: Data quality flags correctly detect K EUR suspect, outlier, high ratio, and no business case conditions.
Tab(s): All (engine-level). Priority: P1 (Must Have).

Display Locations:

Acceptance Criteria:

AC-4: Bubble tooltip shows the correct classification label per programme.

Tab(s): 1, 2, 3, 4, 6. Priority: P1 (Must Have).
BEN-03  Benefit Data Quality Flags
Description: The engine MUST detect and flag data quality issues in benefit claims. Flags are informational and do not block funding (except high ratio which triggers a merit hold).
Implementation:
K EUR suspect: compare impact text numeric values against benefit x 1000. Flag if match found.
Outlier: flag if benefit amount > 100 M€.
High ratio: flag if benefit/cost > 10x. This also triggers the existing merit hold ("Benefit claim above 10.0x — warning only (no funding hold, v5.4)").
No business case: flag if all of benefit (numeric), benefitDetails (text), impact, and problem are empty/null.
Flags stored in benefitFlag field on each programme row.
Programme detail popup MUST display any active flags (updated in v5.3 — see UI-11 for Details table and Funding Rationale label).
Acceptance Criteria:
AC-1: K EUR suspect flag triggers when impact text = benefit x 1000.
AC-2: Outlier flag triggers for benefits > 100 M€.
AC-3: High ratio flag triggers for benefit/cost > 10x.
AC-4: No business case flag triggers when all evidence fields are empty.
AC-5: Flags visible in programme detail popup.
Tab(s): All (engine-level). Priority: P2 (Should Have).

FIN-01  Enterprise-Wide Charging Exclusion
Description: The "Enterprise-wide charging. PMI programmes (type=PMI) are excluded from the prioritisation engine and auto-funded on top off AOP budget" row (Item BU, ~40 M€) MUST be filtered out of all demand records in normalize(). Stored as ewChargingKey on data object for Tab 6 EW split calculation only.
Acceptance Criteria:
AC-1: Enterprise-wide charging. PMI programmes (type=PMI) are excluded from the prioritisation engine and auto-funded on top off AOP budget row does not appear in any table, total, or export.
AC-2: ewChargingKey is accessible for Tab 6 EW distribution calculation.
AC-3: Total demand is 285.1 M€ (not 325.1 M€).
Tab(s): All (engine-level). Priority: P1 (Must Have).
FIN-02  Tab 6 BU Cluster Allocation Table
Description: Tab 6 Organisation IT Cost Allocation table MUST show 7 TCO BU clusters with BU Led, Enterprise Wide, and Operations columns.
Columns:
BU Led (M€): Direct BU-stream funded programmes + Type II cross-BU allocations via source allocation % keys.
Enterprise Wide (M€): Total EW-stream funded demand distributed to BU clusters using the Enterprise-wide charging. PMI programmes (type=PMI) are excluded from the prioritisation engine and auto-funded on top off AOP budget row allocation keys.
Operations (M€): Bill of IT TCO per BU cluster.
Total: Sum of all three columns per row.
Acceptance Criteria:
AC-1: Exactly 7 BU cluster rows (Precision Diagnosis, Connected Care, Image Guided Therapy, Personal Health, EI, Innovation & Design, Int. Property & Standards).
AC-2: Grand Total = BU Led + EW Charges + Operations = Total IT AOP.
AC-3: EW distribution uses normalised proportional allocation keys.
AC-4: Amounts recalculate when scenario changes.
Tab(s): 6. Priority: P1 (Must Have).
FIN-03  EW Charging Key Algorithm
Description: The engine MUST extract sub-org allocation fractions from the Enterprise-wide charging. PMI programmes (type=PMI) are excluded from the prioritisation engine and auto-funded on top off AOP budget row and use them to distribute EW-stream funded demand to BU clusters.
Algorithm:
Source: allocation % columns on the BU sheet for the Enterprise-wide charging. PMI programmes (type=PMI) are excluded from the prioritisation engine and auto-funded on top off AOP budget row.
Map sub-org keys (HPM, MR, G and B, etc.) to BU clusters via SUBORG_BU dictionary.
Normalise proportions so they sum to 100%.
Distribute total EW-stream prioritised demand across BU clusters using normalised proportions.
Acceptance Criteria:
AC-1: All sub-org allocation fractions extracted from source.
AC-2: Fractions mapped correctly to BU clusters.
AC-3: Distributed EW amounts sum to total EW funded demand.
AC-4: Functions/Regions residual shown as separate transparency line when allocation keys are incomplete.
Tab(s): 6. Priority: P1 (Must Have).

Checks:

Acceptance Criteria:
AC-1: All 7 checks run on every scenario change.
AC-2: Critical failures shown with red indicator.
AC-3: Warnings shown with amber indicator.
AC-4: Expand/collapse detail for each check.
Tab(s): 6. Priority: P1 (Must Have).
